# 数据还原排障手册

**适用场景**：一台已经跑过本项目的服务器（Docker 容器和数据卷都还在），要把
`data-export.sh` 导出的那份数据还原上去。

2026-09-14 在正式服务器上从头踩到尾，这份文档是那次的完整记录。下面每条结论都
是当时实测的，不是推测。

---

## 二、理解三样东西分别在哪（关键）

今天所有的坑，根子都是这三样东西**不在一起**：

| 东西 | 在哪 | 删项目目录会怎样 |
|---|---|---|
| `.env`（口令、端口） | 项目目录里 | **跟着没了**（它不进 Git） |
| 数据卷 `exam-system_db_data`（整个数据库） | 归 Docker 管，**不在项目目录里** | **还活着** |
| `exam-data/`（导出的数据 + 口令副本） | 你自己放的地方 | 看你放哪 |

**最要命的一条规矩**：MySQL 的口令**存在数据卷里**，而且**只在第一次建库时**从
`MYSQL_PASSWORD` 取一次，之后再也不看这个变量。

所以：

```
删掉项目目录重新部署
  → .env 没了，deploy.sh 生成一份新的随机口令
  → 数据卷还活着，里面认的是老口令
  → 两边错开，怎么改 .env 都连不上
```

这就是今天反复出现的那个根因。记住这一条，后面的处理都是它的推论。

## 三、卡在「还在等数据库初始化」

### 3.1 这一步在干什么

`data-import.sh` 的 `[4/7]` 只做两件事，**不碰任何数据**：

1. `docker compose up -d db` 把数据库容器拉起来
2. 每 2 秒用 `env.secrets` 里那套账号口令连一次，连上才继续

所以卡住只有两种可能：**容器没真正跑起来**，或**口令和数据卷里的对不上**。

> 卡在这里时按 `Ctrl+C` 是安全的 —— 除了 `.env` 被重写，其它什么都还没动。

### 3.2 一条命令分辨

```bash
cd /opt/A_System_of_WFXXKJ_Simulating_Examination && docker compose ps
```

看 `db` 那行的 STATUS：

- **`Up 4 minutes (unhealthy)`** —— 容器好好跑着，是**认证过不去**。走 3.3。
- **反复 `Up 2 seconds` / `Restarting`** —— MySQL 根本没起来。走 3.4。

### 3.3 认证不通过（最常见）

先花十秒确认：

```bash
docker compose exec -T db sh -c 'mysql -u"$MYSQL_USER" -p"$MYSQL_PASSWORD" -e "SELECT 1" && echo 口令没问题'
```

没打印「口令没问题」就是它 —— 数据卷里一套口令，`env.secrets` 里另一套。

**改 `.env` 没有用**（见第二节那条规矩）。唯一的办法是把这个对不上的卷清掉，
让它按导出的口令重新初始化：

```bash
cd /opt/A_System_of_WFXXKJ_Simulating_Examination && docker compose down && docker volume rm exam-system_db_data
```

```bash
sudo bash scripts/data-import.sh /opt/A_System_of_WFXXKJ_Simulating_Examination/exam-data
```

**清卷之前先确认数据在导出文件夹里**，脚本的 `[1/7]` 会验压缩包完整性，看到
「✓ 四个文件齐全，压缩包完整」+ 清单里的表数量和行数，就可以放心清。

这次会走通：卷是空的，`docker compose up -d db` 拿脚本刚写好的 `.env`
（就是 `env.secrets` 那套口令）初始化，两边不可能再错开。

> **空卷首次建库要三四十秒**，`[4/7]` 会比平时慢，看到「还在等数据库初始化」
> 是正常的，别中断。

### 3.4 容器在重启循环

```bash
docker compose logs db --tail=30
```

日志会直接点明原因（多半是数据卷文件不一致）。这种情况数据卷基本救不回来了，
按 3.3 的办法清卷重来。

### 3.5 为什么脚本以前看不出问题

旧版脚本用 `mysqladmin ping` 判断就绪，而**它口令错了也返回退出码 0**。
在真实 MySQL 上实测过：

```
$ mysqladmin ping -h 127.0.0.1 -u root -p错误口令 --silent
error: 'Access denied for user root@localhost (using password: YES)'
$ echo $?
0
```

于是「就绪检查」形同虚设，一路放行到 `[5/7]` 才报一句没头没脑的
「建库失败，口令可能不对」。同样的原因，`docker-compose.yml` 里数据库的健康
检查也用的它 —— 数据库报「健康」，后端却连不上，报错只说后端不健康。

2.4.1 起两处都改成了**用后端将要用的那套账号真查一次**；2.4.1 的
`data-import.sh` 还会分清「数据库没起来」和「口令对不上」，后者直接问你一句
「清空重来」，不用手敲上面那两条命令。

## 四、部署时后端一直 unhealthy

```
Container exam-system-db-1 Healthy
Container exam-system-backend-1 Error
dependency failed to start: container exam-system-backend-1 is unhealthy
```

同一个根因：删了项目目录重新部署，`.env` 是新口令，数据卷是老口令。
数据库那行显示 Healthy 是因为旧版健康检查用的 `mysqladmin ping`（见 3.5）。

先确认：

```bash
docker compose logs backend --tail=40
```

看到 `Access denied for user 'exam'@...` 或 `(1045` 就对上了。三条路，按顺序试：

**① 找回旧 `.env`（最省事，数据原样不动）**

```bash
ls -a ~ /opt/exam-backups /root 2>/dev/null | grep -i env
ls exam-data/env.secrets 2>/dev/null
```

找到就 `cp 那个文件 .env && chmod 600 .env`，然后 `docker compose up -d`。
`exam-data/env.secrets` 里就是当初那套口令，它最常用。

**② 找不回来但要保住数据**（需要 2.4.1 以上的代码）

```bash
bash scripts/reset-db-password.sh
```

用免密模式起一个临时 mysqld，**先整库导出一份 SQL 备份**，再把库里的口令改成
当前 `.env` 的值。导不出备份就停在原地不改。

**③ 有完整导出，旧数据不要了**

按 3.3 清卷 + 重新 `data-import.sh`。

## 五、还原后端口变回 8080

### 5.1 为什么

`data-import.sh` 的 `[3/7]` 是这么干的：

```bash
cp .env.example .env          # ← 端口从这儿来，模板里写死 8080
# 再把 env.secrets 里有的键覆盖上去
```

而 2.4.2 之前的 `data-export.sh` **只把口令导进 `env.secrets`**
（`MYSQL_* / JWT_SECRET / ADMIN_*`），端口和镜像源不在里面。没人覆盖，就保留了
模板里的 8080。

### 5.2 只改端口，不碰口令

先定一个地址 —— 填**学生浏览器里实际输入的那个**（有域名填域名，走端口转发
填对外那个，不要填内网地址）：

```bash
cd /opt/A_System_of_WFXXKJ_Simulating_Examination && ADDR=你的服务器IP或域名 && sed -i "s#^WEB_PORT=.*#WEB_PORT=3315#" .env && sed -i "s#^CORS_ORIGINS=.*#CORS_ORIGINS=http://$ADDR:3315#" .env && sed -i "s#^PUBLIC_BASE_URL=.*#PUBLIC_BASE_URL=http://$ADDR:3315#" .env && grep -E '^(WEB_PORT|CORS_ORIGINS|PUBLIC_BASE_URL)=' .env
```

`sed` 定点替换，口令那几行一个字都不会碰；最后会把改完的三行打出来核对。

```bash
docker compose up -d
sudo ufw allow 3315/tcp
```

**三行必须一致，别只改第一行**：

| 项 | 管什么 | 填错的后果 |
|---|---|---|
| `WEB_PORT` | 对外开哪个端口 | 打不开网页 |
| `CORS_ORIGINS` | 浏览器允许从哪个地址调接口 | 页面能开，一操作就报错 |
| `PUBLIC_BASE_URL` | 复制给学生的考试链接用什么地址 | 老师复制的链接学生打不开 |

`docker compose up -d` 只重建受影响的容器（前端因为端口变了，后端因为这两个
环境变量变了），**数据库不动，数据不动**。后端重启会重跑迁移和初始化，两者都是
幂等的，库非空时原样跳过。

### 5.3 顺手检查镜像源

旧版 `.env.example` 里**没有 `REGISTRY`**，还原之后这一行大概率也丢了。当下不
影响（镜像已经在本机），但下次 `--build` 时 compose 会退回 `docker.io`，国内拉
不动就会卡住：

```bash
grep -q '^REGISTRY=' .env || echo 'REGISTRY=docker.1ms.run' >> .env
```

### 5.4 验证

```bash
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:3315/api/health
```

`200` 就成了。

## 六、零碎

**`scripts/data-import.sh: No such file or directory`**

你已经在 `scripts/` 目录里了，又写了一遍 `scripts/`。回项目根目录再跑：

```bash
cd /opt/A_System_of_WFXXKJ_Simulating_Examination
sudo bash scripts/data-import.sh /路径/exam-data
```

**题库难度全是 3**

全新部署时题库是从 `legacy/` 那份原卷灌进去的，2.4.4 之前灌库脚本漏了难度，
全吃了默认值。跑一次修复（先试算，确认了再写库）：

```bash
docker compose exec backend python -m tools.fix_difficulty
docker compose exec backend python -m tools.fix_difficulty --write
```

默认只动难度还是 3 的题，老师手工标过的不碰。

## 七、以后不再踩这些坑

1. **别删项目目录重新部署。** 升级用 `git pull && docker compose up -d --build`。
2. **`.env` 单独备份一份**，这是所有麻烦的源头：

   ```bash
   cp .env /opt/exam-backups/env-$(date +%F).bak
   ```

3. **还原成功之后别再跑 `deploy.sh`。** 它发现 `.env` 缺东西就重新生成随机口令，
   立刻又把你打回第三节。以后只用 `docker compose up -d --build`。
4. **绝不用 `docker compose down -v`**，那个 `-v` 会连数据卷一起删。
5. **升级前先导一次**：`sudo bash scripts/data-export.sh`。
   导出失败时脚本绝不打印"完成"，这一点是卡死的。

## 八、新版导出导入（含 2.4.7 及以前的老备份怎么办）

2.4.8 重做了这两个脚本，把前面几节的坑从根上去掉了：

| | 老版本（2.4.7 及以前） | 新版本 |
|---|---|---|
| 导出内容 | `database.sql.gz`（带建表语句）+ `env.secrets`（**含口令**） | `tables/*.jsonl`（只有数据）+ `settings.env`（**无口令**） |
| 还原时 `.env` | 被覆盖成导出时那套口令 | **完全不碰** |
| 还原时表结构 | 被倒退成导出那天的样子 | **完全不碰**，以本机为准 |
| 数据卷 | 口令对不上时要清卷重建 | 不涉及 |
| 备份比系统旧 | 靠 alembic 升回来，新增过表就会炸 | 按列名对齐，新列取默认值、删掉的列跳过并报出来 |

### 用法

导出（在老机器上）：

```bash
sudo bash scripts/data-export.sh
```

还原（在新机器上，**先把系统正常部署好、能打开页面**）：

```bash
sudo bash scripts/data-import.sh /路径/exam-data
```

它会先把本机现有数据备一份回滚点，再试算给你看每张表要导多少行、有哪些版本
差异，确认后才真导。整个导入是一个事务，中途失败会整体回滚。

### `No module named tools.export_data`

脚本是**宿主机上的文件**，`git pull` 就更新了；但 `tools/*.py` 是**打进镜像**的
（`backend/Dockerfile` 里 `COPY . .`，源码没有挂载）。只 `pull` 不重建的话，
新脚本会去调容器里还不存在的模块。

```bash
docker compose up -d --build
```

等后端变成 healthy 再跑。2.4.10 起脚本会提前认出这种情况并直接给出这条命令。

> 这条规律适用于**所有**改了后端代码的升级：`git pull` 之后一定要
> `docker compose up -d --build`，光 `restart` 不会换成新代码。
> 例外是 `config.yaml` 和 `legacy/` —— 那两个是挂载进去的，改完 `restart` 即可。

### 2.4.7 及以前导的老备份

老备份里是 `database.sql.gz`，新脚本认不了，会直接告诉你。两条路：

1. **老机器还在**：用新版脚本重新导一次，一劳永逸。
2. **只剩老备份**：先用老办法把它还原到一台机器上（见第三节），起来之后再用
   新版 `data-export.sh` 导一份新格式的。
